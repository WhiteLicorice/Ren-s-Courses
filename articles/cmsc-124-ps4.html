CMSC 124 Problem Set 4

This is our final battle.

Suppose you have four facts and two rules:

edge(a, b).
edge(b, c).
edge(c, a).
edge(c, d).

reach(X, Y) :- reach(X, Z), edge(Z, Y).
reach(X, Y) :- edge(X, Y).

Now ask whether d can be reached from a:

?- reach(a, d).

Which causes this trace:

reach(a,d)
  clause 1:  reach(a,Z1), edge(Z1,d)
    reach(a,Z1)
      clause 1:  reach(a,Z2), edge(Z2,Z1)
        reach(a,Z2)
          clause 1:  reach(a,Z3), edge(Z3,Z2)
            ...

As you can see it never answers. It doesn't answer false, which would be wrong. Nothing. The program sits there until you stop it.

Now swap the two rules, so that the one whose whole body is edge(X, Y) comes first, and the same question answers true:

reach(a,d)
  clause 1:  edge(a,d)          -> fail
  clause 2:  reach(a,Z), edge(Z,d)
    reach(a,Z)
      clause 1:  edge(a,Z)      -> Z=b
    edge(b,d)                   -> fail
    backtrack into reach(a,Z)
      clause 2:  reach(a,Z2), edge(Z2,Z)
        reach(a,Z2)
          clause 1:  edge(a,Z2) -> Z2=b
        edge(b,Z)               -> Z=c
    edge(c,d)                   -> true (hint: peek at line 3)

Same facts. Same rules. Same logic, in the sense a logician means it, because the two versions say the same thing about reach. The only difference is the order in which they say it.

That's the last idea of the course. It's the reason Prolog is here. Activity 15 built a runtime stack by hand. A frame for every active call, a return address in every frame, and a stack that unwinds when the deepest call returns. Prolog runs on that same machinery and adds one thing: When a call fails, the program goes back to the most recent decision it made and makes a different one. Which decision comes first depends on the order of the rules. In the example above, the first decision is one it never gets back from.

You'll do this in two halves. First you'll predict 16 queries before running any of them, three answers per query, 48 predictions in total, and write why each one comes out the way it does. Then you'll write seven small rules in Prolog, in three groups, ending with the one that walks the graph above and comes home.

This is a paired, asynchronous assignment. It runs on SWI-Prolog alone. One install command gets it. Most of you meet Prolog for the first time here, so Part 1 also tells you which book to read while you work. This manual carries the rules the 16 cases grade. The book teaches the language.

Why These Three Fields?

A Prolog program is a list of facts and rules, together called a knowledge base. edge(a, b). is a fact. It says the relation edge holds between a and b. That's all it says. A rule has a head and a body, head :- body., and it says the head holds whenever every goal in the body does. A query is a question you type at the prompt, and Prolog answers it by searching the knowledge base for a way to make it true.

Take a query with a variable in it:

?- parent(tom, X).

A word that starts with a capital letter is a variable. Prolog looks for a fact or a rule head that matches parent(tom, X), and matching is done by unification, which finds values for variables that make two terms identical. The first parent fact whose first argument is tom unifies, X becomes whatever its second argument is, and Prolog prints that binding.

That's one answer. It isn't the only one. The third field comes from what happens next. At the prompt, Prolog waits after an answer. Press ; and it goes back to the last choice it made, undoes the binding, and looks for the next fact that unifies. That step is called backtracking. Keep pressing ; and it keeps going until the facts run out, when it prints false.

So each case asks three questions:

FieldQuestion
firstWhat is the first answer Prolog prints, in the grader's notation?
secondWhat does the first ; produce, or none when there is no second answer?
countHow many answers does the search find before it says false?

What an Answer Looks Like

An answer is a set of bindings, one for each variable in the query. The grader writes parent(tom, X)'s first answer as X=liz. A query with two variables gets two bindings, joined by a comma, in the order the variables appear in the query. A query with no variables has nothing to bind, so its answer is true. A query with no answer at all reads false.

Two more words cover the cases that don't end that way. When a search runs past the grader's budget, the count reads unbounded, and so does any answer the search hadn't reached when the budget ran out. When a query throws an error, all three fields read error. Two of the 16 cases are unbounded and one is an error. Each of them is there to teach you something.

The Search Has an Order

Two rules decide everything you predict here. Prolog tries clauses in the order they're written, top to bottom. Within a rule body, it tries goals in the order they're written, left to right. That's the whole scheduler.

Those two rules explain the opening example. reach(a, d) tries the first clause, whose body starts with reach(a, Z). To answer that it tries the first clause again, whose body starts with reach(a, Z). No fact is ever consulted. Nothing ever fails, so nothing ever backtracks. The stack grows until something outside the program stops it. Put the edge clause first and each call reads a fact before it recurses. The answer arrives at once. Whether the search then ends is a different question, and P12 asks it.

The goal order inside a body matters just as much. One of the 16 cases turns on it. X > 2 can only be checked when X already holds a number. Ask it before anything has bound X and Prolog throws an error. Ask it after a goal that binds X and it works. Same goals, different order, and one of them is an error row in your table.

Learning Objectives

By the end of this problem set, you should be able to:

  • Read a fact, a rule, and a query, and say what each one claims
  • Unify two terms by hand, and say which variable ends up bound to what
  • Predict the first answer to a query by following clause order and goal order, without running it
  • Predict what backtracking finds next, and when it finds nothing
  • Explain why swapping two clauses can change the order of the answers, and why in one case it changes whether the search ever answers
  • Write a recursive rule with a base case that reads one fact and a recursive case that asks a smaller question
  • Write a rule over lists, using the [Head|Tail] pattern
  • Carry a visited list through a recursive walk so that a cyclic graph can't trap it
  • Read a four-port trace of a search and match its lines to frames being pushed and popped on the runtime stack from Activity 15

The Knowledge Base Has No Cut

If you've read ahead, you may have met !, the cut, and \+, negation. cases/kb.pl uses neither, and it says so at the top. The tracer behind ./trace walks the knowledge base one clause at a time and reports every step. A cut lets a clause skip steps the tracer can't see. Keeping the base plain keeps the trace honest. Your own rules in Part 2 may use \+. The last group needs it. They're graded on their answers and never traced.

The Rules You Need

A term is anything Prolog can talk about. tom is an atom, a name that stands for itself. 3 is a number. X is a variable. parent(tom, X) and f(Y, a) are compound terms, a name followed by arguments in parentheses. [a, b, c] is a list, which is a compound term wearing a convenient costume.

Unification makes two terms identical by binding variables, when that's possible. f(X, b) unifies with f(a, Y) by binding X to a and Y to b. a doesn't unify with b, because two different atoms are different and no binding can change that. X = f(Y, a) doesn't compute anything. It unifies X with the term f(Y, a), leaving Y inside it unbound, and a later Y = b fills that in. The = you see in three of the cases is unification and nothing else.

A query is answered by finding a clause whose head unifies with it. For a fact, that's the whole job. For a rule, the goals in the body become new queries, tried left to right. When every goal in the body succeeds, the head succeeds with whatever bindings the body made. When a goal fails, Prolog backtracks to the most recent goal that still has untried clauses, undoes the bindings made since, and tries the next one.

That machinery decides how grandparent(tom, X) plays out. The rule is grandparent(G, C) :- parent(G, P), parent(P, C). Prolog binds P to tom's first child, then asks whether that child has a child. If not, it backtracks, rebinds P to tom's second child, and asks again. The facts are written in an order that makes this happen, and ./trace P07 shows it.

Recursion in Prolog is a rule that calls itself with a smaller question. ancestor(A, D) holds when parent(A, D) does, and also when A is a parent of someone who is an ancestor of D. The base clause reads one fact. The recursive clause reads one fact and then asks a smaller question. Which clause comes first decides the order the answers come out in, and P08 and P09 are the same question asked of two clause orders.

A list is written [a, b, c]. The pattern [H|T] unifies with any nonempty list, binding H to its first element and T to the rest. [] is the empty list and matches nothing else. Every list rule you'll meet has a clause for [] and a clause for [H|T], which is the base case and the recursive case again.

Arithmetic needs is. N is M + 1 computes the right side and unifies the result with N. N = M + 1 would unify N with the compound term M + 1. No number would ever appear. Both is and the comparison > need their operands bound to numbers already. Ask X > 2 while X is unbound and Prolog throws an instantiation error, which is a precise way of saying "you asked before you told me."

Three mechanical rules go with the table. Elements and bindings are separated by commas and nothing else. Predict, Then Commit

Replace every TODO in predictions.tsv. Keep the tab-separated layout and the case order. Then check the table's form:

./lint

./lint reads the form only. It never opens tests/expected.tsv and never runs a case, so it tells you nothing about whether an answer is right, and that's what makes it safe to run before the prediction commit. What it catches is the class of mistake that costs marks for no reason. A padded cell, a space inside an answer, a count that isn't a number. Those all survive the parse and then fail their comparisons, so they read like wrong predictions. Others are worse. A tab your editor replaced with spaces, or a missing or reordered row, stops the grader before it scores anything. One trailing space on every answer row fails all 16 count checks. Each failure prints as FAIL P01.count, a label that never mentions a space.

It reports each fault with its line and column:

line 3, column count: "one" is neither a whole number, unbounded, nor error. A
search that ends has 0 or more answers, one that never ends reads unbounded,
and one that throws reads error.

Line 3 is P02. The header is line 1.

Now the reasoning. A right answer can be copied from the table, and ./run prints every one of them, so the answers alone can't show the work. The grade turns on why each case comes out the way it does. That's what REASONING.md holds: one entry per case, written before you run anything, naming the rule that fixes each field. The starter ships the file with a heading for every case and one placeholder line under each. Replace each placeholder with one to three sentences.

The grader checks the structure of the file, not the prose. It wants every heading ## P01 to ## P16 in order, a non-blank line under each, and the placeholder line gone. There's no word minimum, because a minimum invites padding. What it can't see is whether your reasoning is any good. That part is a rubric call, and it rewards an entry that names a rule over one that restates the answer.

An entry looks like this. The example case isn't one of the 16, so it gives nothing away:

The goal scans the parent facts in source order and takes the first whose
first argument is pat. Only parent(pat, jim) matches, so X binds to jim.
No fact is left, so the first ; finds nothing and the count is 1.

git add predictions.tsv REASONING.md

That commit records your prediction before you inspect a case or open tests/expected.tsv. Git stamps when REASONING.md first appeared, so reasoning added after you run the cases doesn't read as a prediction. Write it first, because a later entry doesn't carry the grade.

./run P01

Watch the Search

When a row surprises you, don't reread the rules. Watch the search:

./trace P07

== trace P07 ==
Call: grandparent(tom,X)
  Call: parent(tom,_)
  Exit: parent(tom,liz)
  Call: parent(liz,X)
  Fail: parent(liz,X)
  Redo: parent(tom,liz)
  Exit: parent(tom,bob)
  Call: parent(bob,X)
  Exit: parent(bob,ann)
Exit: grandparent(tom,ann)
answer 1: X=ann
Redo: grandparent(tom,ann)
  Redo: parent(bob,ann)
  Exit: parent(bob,pat)
Exit: grandparent(tom,pat)
answer 2: X=pat
Redo: grandparent(tom,pat)
  Redo: parent(bob,pat)
  Fail: parent(bob,X)
  Redo: parent(tom,bob)
  Fail: parent(tom,_)
Fail: grandparent(tom,X)
== 2 answers ==

Every goal in a search passes through four doors. The trace prints one line each time it goes through one. Call is the goal being tried for the first time. Exit is the goal succeeding, with the bindings it made shown in place. Redo is the search coming back to the goal after something later failed, to try its next clause. The record it comes back to, which clause matched and that more remain, is a choice point. Activity 15's returned frames kept no such record. Fail is the goal running out of clauses. Indentation is depth. A goal's body sits one level below it. These are the same four words that swipl's own debugger prints, with the keystrokes removed.

Read the trace above once with the rule for grandparent beside it. P binds to liz first because that's the first parent(tom, _) fact. liz has no children, so parent(liz, X) fails. The search goes back through Redo to the fact that bound liz, undoes that binding, and takes the next fact. That's the whole of backtracking, in six lines.

Two of the cases stop the tracer at 400 lines with a message. That's the tracer giving up, not the search ending. Read the goal that repeats and you'll see why it won't.

Part 2: Write the Rules

Now you write rules of your own, against the same facts.

src/rules.pl is loaded after cases/kb.pl, so parent/2, edge/2, elem/2, join/3, and len/2 are yours to call. The notation name/2 means a predicate called name that takes two arguments. elem(X, L) holds when X is an element of L. join(A, B, C) holds when C is A followed by B. len(L, N) holds when L has N elements. All three are defined in the knowledge base. P13, P14, and P16 trace them.

The grader scores three groups independently. A pair that finishes R1 and R2 and never gets route/3 to end keeps every mark from R1 and R2. Work in order.

Each stub in the file throws when called, so a check you haven't reached fails with a message that says which predicate is missing. Replace the whole stub, head and body, with your own clauses. A stub left above your clauses runs first and throws before yours are ever tried.

R1: The Family

R1 is three rules over parent/2.

sibling(X, Y) holds when X and Y share a parent and aren't the same person. The second half is X \= Y, which succeeds when its two sides can't be unified. X \= Y with either side unbound fails at once because an unbound variable unifies with anything. Put it before the goal that binds them and sibling(ann, X) answers nothing. Put it after and it works. One of the six R1 checks asks that query.

cousin(X, Y) holds when a parent of X and a parent of Y are siblings. Use the rule you just wrote.

descendant(D, A) holds when A is an ancestor of D. Write it as the mirror image of ancestor/2 in cases/kb.pl, two clauses, base first. The grader checks the set of descendants and the set of ancestors and ignores their order, so a different definition that finds the same set also passes. The suggested one is the one you'll be able to follow by hand, one clause at a time.

?- sibling(ann, X).
X = pat.

?- cousin(sue, X).
X = jim ;
false.

?- descendant(sue, X).
X = ann ;
X = bob ;
X = tom ;
false.

R2: Lists

Three rules over lists, each with a base case and a recursive case.

count_of(X, List, N) holds when X occurs N times in List. The empty list holds zero of anything. That's your base case. For a nonempty list, the head either is X or isn't, so the count is the tail's count plus one, or the tail's count unchanged. Write those as two clauses. The one for "isn't" needs X \= H, and by now you know where to put it.

rev(List, Reversed) holds when Reversed holds the elements of List in the other order. Reverse the tail, then use join/3 to put the head on the end. This is the classic naive reverse. It has a property you should see once. Run it backward:

?- rev(X, [1, 2]).
X = [2, 1] ;

The first answer is right. Press ; and it never comes back. The recursive call rev(T, RT) has both arguments unbound, so it enumerates lists of every length looking for one whose reverse is [1, 2], and there's no length at which it can stop. The grader asks for the first answer only, under a budget. Your rev is correct if it finds [2, 1] first. It isn't wrong for looping afterward. That's the definition doing what it says.

last_of(List, X) holds when X is the last element of List. A one-element list's last element is that element. The empty list has no last element, so last_of([], X) must fail, and it does on its own if you don't write a clause for [].

R3: The Graph

One rule, the one the opening example was about.

route(From, To, Path) holds when Path is the list of nodes from From to To, in order, following edge/2 and never visiting a node twice. A route from a node to itself is [From].

?- route(a, d, P).
P = [a, b, c, d] ;
false.

?- route(c, b, P).
P = [c, a, b] ;
false.

The graph has a cycle, a to b to c and back to a. reach_r/2 in the knowledge base walks this graph without remembering where it's been, and P12 shows what that costs. It finds true. Press ; and it goes round the cycle, finds true again, and never stops finding it. That's why P12's count is unbounded. route/3 has to be the version that comes home.

The standard way is a helper that carries the visited list, something like travel(From, To, Visited, Path). Visited holds every node seen so far. The base case is reaching To. The recursive case takes one edge to a Next, refuses it when Next is already in Visited, and continues from there with Next added. "Refuses it" is where \+ comes in. \+ Goal succeeds when Goal can't be proved. So \+ elem(Next, Visited) says "not yet visited." Chapter 10 of the book explains why this is called negation as failure. It also explains why it's only safe when Next is already bound. It's here, since edge(From, Next) ran first.

If you build Visited by adding to the front, the finished list comes out backward. You have a rev/2 from R2.

Each query that a check in R1, R2, and R3 asks runs under a budget of 200,000 inferences. The model solution spends under 150 on any one query. A route/3 that goes round the cycle fails those checks with a message that states the budget, and so does a rule that repeats its work thousands of times over. Your run doesn't hang.

Part 3: Explain the Search

Replace the placeholder in ANALYSIS.md with 300 to 450 words written by both partners, plus one pasted trace. The grader counts every space-separated token in the file, so a heading counts too, and it skips the lines a ./trace produces, so the trace costs you no words. It fails while the placeholder text is still there. It fails again when the total lands under 300 or over 450. It enforces both limits. Aim for the middle, so one last round of editing leaves you inside the range.

Paste the output of ./trace for one case, then answer these:

  • Which lines in your trace are a frame being pushed onto the runtime stack from Activity 15, and which are a frame being popped?
  • A Redo line resumes a goal that already exited. What does that goal still know that a returned frame in Activity 15 had already thrown away?

Common Pitfalls

  • Forgetting the period. Every clause in a file and every query at the prompt ends with one. Without it, the prompt waits and the file won't load.
  • Reading = as assignment. It's unification. X = f(Y, a) builds nothing and computes nothing. It makes X and f(Y, a) the same term.
  • Using = where you meant is. N = M + 1 binds N to a compound term named +. Only is does arithmetic.
  • Asking > or is before the operands are bound. That's an instantiation error, and one of the 16 cases is built to show it.
  • Putting X \= Y before the goals that bind X and Y. It fails on the spot, and sibling(ann, X) answers nothing.
  • Predicting an order without following the clauses. ancestor and ancestor_r find the same six people. Their first answers differ.
  • Predicting false for a search that never ends. The search doesn't say false. It doesn't say anything, and the table says unbounded.
  • Writing an answer with spaces in it. The comparison is exact, so X = liz is a wrong answer to a case whose result is X=liz. Run ./lint and it prints the line and column of each fault before a check ever scores it.
  • Walking the graph without a visited list. Every R3 check runs under a budget and tells you when the walk didn't come home.
  • Leaving a stub above your own clauses. The stub runs first and throws.
  • Running the cases before committing predictions. The Git history would no longer establish which answers were predictions.
  • Leaving the placeholder line under a case in REASONING.md. The file has to carry the reasoning, not the template. The grader names the case it finds.
  • Writing the reasoning after you run. The prediction commit is where it counts, and Git shows when each entry first appeared.
  • Editing tests/expected.tsv until the checks pass. The published copy replaces it during grading.
