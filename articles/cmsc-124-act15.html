Building the Runtime Stack

CMSC 124 Activity 15

Ren• November 12, 2026
Download
>>Table of Contents

Recursion doesn't reuse one set of locals. Every active call needs its own parameters, locals, return point, and links to other frames. Today you'll build that stack at its deepest point, resolve nonlocal identifiers, and then unwind it without dropping a return value.

The programs here are pseudocode. They're written to be read. You don't need another language's syntax rules. We'll use one frame per call, even when a compiler could reuse a frame for a call immediately followed by return. That reuse is called tail-call optimization. We won't apply it here. Evaluate expressions from left to right.

You have 60 minutes for the three checkpoints. Keep each worked example beside the checkpoint it supports. Discussion with classmates and the instructor is allowed and encouraged throughout. This activity is worth 22 points. Twelve points reward runtime constructions, and ten reward explanations.

The Frame Contract

Start with this smaller program. In this pseudocode, main textually encloses outer, and outer textually encloses walk. A textual parent is the procedure whose scope contains another procedure's definition. Use those nesting rules throughout the activity.

main:
    base = 2
    result = outer(1)

    outer(n):
        offset = 3

        walk(k):
            local = k
            if k == 0:
                return base + offset + local
            return walk(k - 1)

        return walk(n)

An activation record, or stack frame, stores the information for one active call. A call pushes a fresh frame. Returning pops that frame. A suspended call is an unfinished caller waiting for a called procedure to return. Use these fields:

FieldPurpose
Parameters and localsThe call's own data
Return addressThe instruction to resume after this call returns
Saved stateThis call's pending operands, kept while a deeper call runs
Dynamic linkThe caller's frame
Static linkThe frame for the textually enclosing procedure

The dynamic chain follows calls. The static chain follows lexical nesting and supports access to nonlocal variables. A recursive call creates a fresh frame even though it runs the same code.

Here, saved state records a pending operand in the frame of the call that still needs it. With return walk(k - 1), there's no pending addition, so write none. The parameters and locals remain in their own fields. Checkpoint 3 adds a pending operand.

Machines also preserve registers according to their calling conventions, the rules for calls and returns. You don't need to invent registers for this paper model. The drawings use conceptual fields. Their physical layout depends on the implementation.

Finally, add the links. Ask two separate questions for each new frame. Who made this call? That frame is the dynamic-link target. Which procedure contains this definition in the source? Its active frame is the static-link target.

For walk(0), the caller is walk(1), but the definition of walk sits inside outer. The dynamic link reaches walk(1). The static link reaches outer. Calling walk again executes the same definition inside outer, so another recursive frame never becomes its textual parent.

Running Case

All three worked examples use the smaller program's base=2, offset=3, and outer(1). All three checkpoints start from this larger program. point P marks the inspection location. It executes no statement and creates no frame. Stop there before evaluating the following return expression.

main:
    base = 10
    result = outer(2)
    print(result)

    outer(n):
        offset = 2

        walk(k):
            local = k
            if k == 0:
                point P
                return base + offset + local
            return walk(k - 1)

        return walk(n)

The indentation keeps the same textual nesting. The extra recursive level adds a walk(2) frame before walk(1) and walk(0). Draw the newest frame at the top. print(result) must wait until outer(2) returns and result receives its value.

Resolve the Nonlocal Names

A lookup finds the declaration used by an identifier and reads its value. Nonlocal identifiers have declarations outside the current procedure. Here, local belongs to walk, offset belongs to outer, and base belongs to main.

Our programs use static scope. Start in the current frame. If that procedure has no matching declaration, follow its static link to the enclosing procedure's frame. Repeat until the declaration is found. Stop at that declaration. The source nesting determines this path.

If the Language Chose Dynamic Scope Instead

The three checkpoints all use static scope. This section compares two ways to implement dynamic scope, the alternative rule from Activity 9. Under dynamic scope, lookup checks the current call and then its callers. It selects the first matching active declaration.

Deep access performs that search through dynamic links. For offset at point P, the larger program's path would be walk(0) -> walk(1) -> walk(2) -> outer. The first three frames have no offset, so lookup reads outer's 2 and stops. It never visits main. If no matching declaration exists anywhere on the path, lookup fails.

One form of shallow access keeps a separate stack of active bindings, associations between identifiers and their storage. When a declaration becomes active, push its binding. When its scope ends, pop that binding. A read uses the top binding directly. For the same point P:

IdentifierBinding values, oldest to newestValue read nowValue after walk(0) returns
local2, 1, 001
offset222
base101010

The three local bindings belong to different calls. Removing the newest exposes walk(1)'s 1. It doesn't alter either remaining value. If a binding stack is empty, a lookup of that identifier fails.

Deep access examines frames on each read. Shallow access avoids that traversal but must maintain binding stacks at scope entry and exit. Both implement dynamic scope. Static scope instead uses the declarations selected from source nesting and reaches their active frames through static links.

Where a Block Lives

A block groups statements and can introduce a scope for its declarations. As a separate storage example, replace the larger program's walk body with this version:

walk(k):
    local = k
    if k == 0:
        temp = local * 2
        return base + offset + temp
    return walk(k - 1)

Here, the if body is a block, and temp belongs to that block alone. walk(1) skips the body, so it creates no active temp binding. walk(0) enters it, initializes temp = 0 * 2 = 0, and uses that value in its return. Entering the block makes no procedure call.

One implementation gives each block a separate record. Another reserves storage inside the enclosing procedure's frame. Use the second model here. Each walk frame can reserve a slot for temp, even while that block's binding is inactive. Reserving space doesn't run the initialization or make temp visible outside its block.

With these fixed-size variables, the compiler can determine the slot's offset, its distance from the frame's base. That storage distance is independent of the program variable offset in outer. No extra frame is needed for this block in our model.

The procedure frame must hold all block variables whose lifetimes overlap. An inner block can be active while its enclosing block remains active, so both need storage. Blocks whose variable lifetimes never overlap may reuse slots.

Storage reuse and shadowing answer different questions. Shadowing occurs when an inner declaration hides an outer declaration of the same identifier. The outer binding can remain alive while hidden. It still needs storage for a value that becomes visible again when the inner scope ends.

Where That Leaves You

Your three traces give the runtime three jobs. A call creates storage for its own parameters and locals. A lookup reaches the declaration selected by the language's scope rule. A return delivers a value and resumes a caller that still has work to finish.

The Prolog problem set, ps4, adds saved search information. A choice point records remaining alternatives and enough state to try them later. Backtracking returns to the most recent remaining choice point, undoes bindings made since it, and tries the next alternative. This requires information beyond the ordinary call-and-return frames you drew. It needn't occupy the same physical record as a call frame.

That problem set asks you to distinguish calls and returns from a search trying another clause. Your interpreter also needs to preserve each unfinished call's data and resume action. The drawings show what that bookkeeping must accomplish.
