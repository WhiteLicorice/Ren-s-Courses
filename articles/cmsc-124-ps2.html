Data in R

CMSC 124 Problem Set 2

Ren• October 13, 2026
Download
>>Table of Contents

Suppose you run this expression:

c(TRUE, 2L, 3.5)

The result is a vector containing 1, 2, and 3.5. That answer hides the part R decided for you. The logical value became a number, the integer became a double, and the result kept length 3 without gaining dimensions. One line crossed the data-type questions from Unit 5 and the coercion questions from Unit 6.

Last week you built ten data types by hand in C, where a value becomes another type only because you wrote the code that converts it. R is the other extreme. Types belong to values at runtime. A name can later refer to a value of another type. R also converts values on its own. Sebesta calls an implicit type conversion coercion. This problem set uses his term mixed-mode assignment for subassignment that widens an atomic vector so a new value fits.

This problem set makes those decisions visible. You'll predict 16 expressions before you run them. Each prediction has four parts: value, typeof, length, and dimensions. Then you'll write the same score transformation twice. One version uses R's vector operations. The other visits one element at a time. Their outputs must agree, but they get there through different evaluation models.

This is a paired, asynchronous assignment with seven full workdays. It uses only base R, so package installation can't become the assignment by accident. Most of you meet R for the first time here, so Part 1 also points to the guide you're expected to read while you work. This manual carries the rules the cases grade. It doesn't replace the introduction to R in the required reading.

A Small R Syntax Map

The opening expression already uses two R conventions. c() combines its arguments into a vector. The L suffix makes 2L an integer, while a bare 2 is a double. R has no separate scalar data type. This problem set calls an operation scalar when it works on one element at a time. Each extracted element is still a length-one vector.

R usually writes assignment with <-. In x <- 1:3, R evaluates the right side and binds the result to x. The : operator builds the integer sequence 1, 2, 3. Braces group several expressions into one block. R evaluates the block from top to bottom. Its last expression supplies the block's value.

The case corpus wraps each expression in quote(). That function stores an unevaluated call as a language object, which lets the runner choose and evaluate one case later. It doesn't run the call when cases.R loads.

Labels inside c() become the vector's names attribute:

x <- c(first = 8L, second = 5L, third = 9L)
x[c(3L, 1L)]

The index requests positions 3 and 1 in that order. The selected values keep the attached names in the same order.

Why Four Predictions?

In R, the printed value is only one part of an object's behavior.

data.frame(id = 1:2, passed = c(TRUE, FALSE))

This prints like a table. Underneath, typeof() reports "list", length() reports 2, and dim() reports two rows by two columns. The four observations answer different questions:

FieldQuestion
valueWhat values does the expression produce, and in what order?
typeWhat storage mode does typeof() report?
lengthHow many top-level elements does length() count?
dimDoes the object carry dimensions, and what are they?

A matrix drives the distinction home. A 2 by 3 matrix has length 6 because six values live in it. Its dimensions are 2x3 because R also remembers how to arrange them. A plain vector of those six values has the same length and no dimensions.

typeof() Is Not class()

The type field asks what the object is made of. The class field asks how the object acts. R answers those questions with two functions that often disagree.

x <- data.frame(id = 1:2, passed = c(TRUE, FALSE))
typeof(x)   # "list"
class(x)    # "data.frame"

A data frame acts like a table, so class() says data.frame. It's built out of a list of columns, so typeof() says list. A factor tells the same story in different words. It acts like a set of labels but stores integers, so class() says factor while typeof() says integer:

y <- factor(c("red", "blue", "red"))
typeof(y)   # "integer"
class(y)    # "factor"

Nothing about y is a character value. The labels you see printed are the level names, and what the vector holds is the codes that point at them.

Predict what typeof() reports. Every case in this set asks for storage, so when your instinct hands you the word you'd see in a printout, it's probably handing you the class.

The grader uses a compact spelling for values. Square brackets hold an atomic vector, matrix[2x3](...) includes the dimensions, and list{...} shows the top-level items of a list. Part 1 gives the complete notation with an example of every form. This is grader notation. It isn't R syntax.

Four fields also mean four reasons a prediction can miss. A wrong value often points at one rule and a wrong type at another, so four fields turn one guess into a short diagnosis. REASONING.md, which Part 1 introduces, is where you write that diagnosis down before you run anything. Predicting the value alone would hide which rule decided the storage.

The Rules You Need

An atomic vector stores one basic type. When c() combines logical, integer, double, or character values, R converts the whole vector to a common type. A list can keep unlike types in separate elements.

For the four atomic types in this assignment, R climbs a coercion ladder from logical to integer to double to character. It stops at the highest type present. c(TRUE, 2L) gives you integers. Add a 3.5 and the whole vector becomes double. Put a string anywhere in it and every element becomes character, including the logical value, which becomes "TRUE".

R applies most arithmetic operators element by element. If one operand is shorter, R repeats it. This is recycling. In a 4-element vector plus a 2-element vector, the shorter operand contributes its first element to positions 1 and 3, then its second element to positions 2 and 4.

Recycling doesn't require the lengths to divide evenly. Add a 2-element vector to a 3-element one and R recycles anyway, reusing the first element a third time and printing a warning while it does. The result still comes back. A warning isn't an error, so a script that produces one keeps running and hands you an answer built on a partial repeat.

A matrix recycles the same way, but you have to know how a matrix is laid out first. R fills and stores one by columns, so matrix(1:6, nrow = 2) puts 1 and 2 in the first column, 3 and 4 in the second, 5 and 6 in the third. Underneath it's still the vector 1 2 3 4 5 6 with a dim attribute attached. Adding c(10, 20) recycles that pair down that same underlying order, so 10 goes to the first, third, and fifth stored values while 20 goes to the second, fourth, and sixth. In a two-row matrix that works out to adding 10 to every entry in the top row and 20 to every entry in the bottom one. Read the matrix by rows instead and you'll predict the additions backward.

R indices begin at 1. Positive indices select positions. Negative indices exclude positions. A logical index selects positions where the corresponding logical value is TRUE. Index 0 selects nothing and returns a zero-length result of the same atomic type.

The single bar in a | b computes logical OR at every position. TRUE | NA is TRUE because the known operand already determines the result. FALSE | NA is NA. This rule lets is.na(x) | x > 10L select a missing element even though comparing that element with 10L produces NA.

NA is a missing value. Arithmetic with a missing operand usually produces a missing result. Comparisons do too. Functions such as mean() accept an na.rm argument when removing missing values is a meaningful choice.

ifelse(test, yes, no) makes one choice per position. It takes the value from yes where test is TRUE and from no where test is FALSE. A length-one yes or no value repeats across the required positions.

A factor stores integer codes and carries a set of level labels. A matrix and an array are atomic vectors with a dim attribute. A data frame is a list of equal-length columns with row and column dimensions.

Subassignment can change more than a value. If an integer vector receives a double, R widens the whole vector to double so the new value fits. That's a mixed-mode assignment. It retypes the existing elements along with the slot you wrote to.

Part 2: Implement the Score Transformation

The prediction cases culminate in this transformation:

scores <- c(7, NA_real_, 12, 4)
adjusted <- ifelse(is.na(scores), 0, scores * 2)
adjusted[adjusted > 15] <- 15
adjusted

You now implement a related operation in two ways. Both functions receive a numeric vector, including its names attribute when present. For each element:

  1. Replace a missing score with 0.
  2. Double every nonmissing score.
  3. Cap the result at 20.
  4. Preserve the vector's names attribute.

The snippet at the top of this part is prediction case P14's body. It caps at 15. Your transformation caps at 20. That's why the sample shows Linus at 20. His 12 doubles to 24 before the cap.

For the published sample:

c(Ada = 8, Grace = NA_real_, Linus = 12, Barbara = 4)

both functions return:

c(Ada = 16, Grace = 0, Linus = 20, Barbara = 8)

Implement clean_scores_vector() with vector expressions and subassignment. Don't use for, while, repeat, Map, lapply, sapply, or vapply in that function.

Implement clean_scores_scalar() with a for loop and one element at a time. Don't call clean_scores_vector() from it. The loop gives you an element-at-a-time evaluation model to compare against R's usual vector model. The word scalar describes that implementation strategy. R still represents each selected score as a length-one vector.

What the Model Checks Can't See

Two of the 76 checks look at how your cleaners work rather than what they return. clean_scores_vector_model reads the calls in the vector function and fails if any of them is a forbidden one. clean_scores_scalar_model rewrites each for loop in the scalar function so it counts its own passes, then runs the rewrite on a four-element vector. It wants the right answer and at least one pass per element. It also fails a direct call to clean_scores_vector().

Neither check can prove which evaluation model you used. The reason is R's semantics showing through. Each of these gets past one of the checks:

  1. A loop that runs once per element and does nothing, followed by a vector expression that computes the answer. The counter sees four passes. It can't see that they were idle.
  2. A scalar function that inspects its own body while it runs, finds the counter the check added, and bumps it. A function body is an ordinary language object in R, so the counting code is open to the code it measures.
  3. delegate <- clean_scores_vector, then delegate(scores). A function is a value like any other. Binding it to a second name doesn't copy anything, and the check only looks for the first name.
  4. A vector function that hands its work to a helper with a loop inside. The check reads one function body, and the helper's body lives somewhere else.

All four come from the same fact. Names bind to values at runtime, and a function is just another value. A check that runs in the same R session as your code is reasoning about code that can rename, rewrap, or rewrite whatever the check looks at. Moving the check into a separate process doesn't help either. The process that runs your function is still an R session your code controls. The only automatic fix left is a rigid template for both functions. That would reject most correct solutions.

So the two checks guard against honest slips. The rest is a rubric call. Your source gets read during grading, helpers included. A submission that games either check is graded on what its source does, not on what the checker printed, and a deliberate bypass falls under a Poor rubric band below. It's also more work than just writing the function itself properly.

Build the Data Frame

Implement:

build_roster(student_names, groups, scores)

It returns a data frame with these columns in order:

ColumnRequired value

Set stringsAsFactors = FALSE when constructing the data frame. The group column is already an explicit factor.

"Levels follow first appearance" is a rule with mechanics behind it, so run them once before you rely on it:

groups <- c("red", "blue", "red", "blue")

levels(factor(groups))                           # "blue" "red"
levels(factor(groups, levels = unique(groups)))  # "red"  "blue"

factor() sorts its levels when you don't supply them. For these two labels, sorting inverts the required order. unique() returns the distinct values in the order they first appear, which is the order the column has to carry. The level order is what decides the row order of anything grouped by this column later. An incorrect order here first becomes visible in summarize_roster.

Summarize the Data Frame

Implement:

summarize_roster(roster)

It returns a list with these items in order:

Use vector expressions to select rows and compute these values. For the published sample the factor's levels are red then blue, so mean_by_group comes out as c(red = 18, blue = 4).

mean_by_group has to be a named vector of doubles with no dimensions. That rules out tapply(), which looks like the right tool and returns a one-dimensional array instead. A c() with red and blue written by hand works only for the sample. The grader also runs a roster with other groups.

Follow the Missing Value

Grace's NA is the element that makes the two implementations look different, so follow that one element through each of them.

The vector version never mentions Grace. Three whole-vector operations run in order. Her element is carried along by each one:

StepThe operation on the whole vectorWhat happens to Grace's element
1an is.na() mask used to subassign 0NA becomes 0
2arithmetic across the whole vector0 * 2 is 0
3a comparison mask used to subassign the cap0 > 20 is false, so 0 stays

Each row is one expression. The mask in rows 1 and 3 is a logical vector the same length as scores, and putting that mask inside [ ] on the left of <- is the subassignment the constraint asks for. That's what "vector expressions and subassignment" means in practice.

The scalar version reaches Grace on its second pass. Nothing else in the vector takes part:

PassElementWhat the loop body does
1Ada, 8present, so double to 16, which is under the cap
2Grace, NAmissing, so store 0 and skip the doubling
3Linus, 12present, so double to 24, then cap at 20
4Barbara, 4present, so double to 8, which is under the cap

Both tables end at the same four numbers. What changes is how the code refers to Grace. The vector version applies three expressions to the full vector and never refers to position 2. Its first mask makes the missing-value decision. The scalar version makes that decision during the second loop iteration, at a line where a debugger could stop.

The loop has one trap the vector version avoids. Copy scores into a local double vector with setNames(as.double(scores), names(scores)), since a bare as.double() strips the names attribute. Write elements back with out[[i]] <- value and the names attribute stays attached. Accumulate into a fresh vector with out <- c(out, value) and the names come out missing, which fails the check even though all four numbers are right.

Read that heading first when it appears. A fault listed there identifies a typing mistake before the grader scores a prediction.

check.sh exits 0 only when all 76 checks pass. A runtime error in one of your functions becomes a labeled failed check while the script continues. Start at the first failure.

Malformed prediction tables stop the grader before it scores anything. The table has to keep its five columns and all 16 ids in order. When it doesn't, the script says so and quits. A run without a == result == line points to the layout of predictions.tsv. A stray tab, a deleted row, or spaces in place of tabs can cause that failure.

Common Pitfalls

  • Reading a factor's printed labels and predicting character. typeof() reports its integer storage.
  • Writing a value description with spaces in it. The comparison is exact, so [1, 2] is a wrong answer to a case whose result is [1,2]. Run ./lint and it identifies the cell before a check ever scores it.
  • Treating a data frame's length as its row count. A data frame is a list of columns, so length counts columns.
  • Reading a matrix left to right by rows. R fills and stores matrices by columns unless told otherwise.
  • Assuming arithmetic stops when the shorter vector ends. R recycles it.
  • Comparing NA with a number and expecting TRUE or FALSE. The comparison is missing too.
  • Using mean() on data containing NA without deciding whether to remove the missing values.
  • Dropping the names attribute from the cleaning result.
  • Implementing the scalar function by calling the vector function. The outputs would pass through the same evaluation path, leaving nothing to compare.
  • Running the cases before committing predictions. The Git history would no longer establish which answers were predictions.
  • Leaving REASONING.md for after the run. Entries written once the answers are on screen are corrections, not predictions, and the grade reads the reasoning against the prediction commit.
  • Editing tests/expected.tsv until the checks pass. The published copy replaces it during grading.
