LISPing Your Functions

CMSC 124 Problem Set 3

Ren• October 29, 2026
Download
>>Table of Contents

Suppose you run this:

(let ((factor 2))
  (let ((f (lambda (n) (* n factor))))
    (let ((factor 10))
      (funcall f 3))))

The answer is 6.

Read it again. By the time f runs, the nearest factor in sight is 10, and 30 is the answer a great many people write down. Lisp says 6, because f didn't look up factor when it ran. It captured factor when defined. The binding it caught held 2. The factor bound to 10 arrived later, and f never saw it.

That's the closing idea of Unit 8. Activity 14 traced it through a C++ lambda. Create the function, return it from the factory, call it somewhere else, and watch it still reach the variable that made it. This problem set is where you make that behavior yours by building the machinery that produces it.

You'll do it in two halves. First you'll predict 16 Lisp forms before running any of them, four answers per form, 64 predictions in total. Then you'll write a small evaluator for a toy language in Common Lisp, in four stages, ending with the stage that decides whether the form above is 6 or 30.

This is a paired, asynchronous assignment. It runs on GNU CLISP alone, so installation can't accidentally become the assignment. Most of you meet Lisp for the first time here, so Part 1 also tells you which book to read while you work. This manual carries the rules the 16 cases grade. The book below teaches the language.

Why The Four Fields?

Common Lisp calls anything meant for evaluation a form. A form can be an atom, such as 3 or factor, or a nonempty list. A nonempty list used as code is a compound form. That same list can also be data. This shared representation lets the same parentheses mean "call this" or "here, have this list." The kind field records what evaluation returned.

Take a form that looks like arithmetic:

(quote (+ 1 2))

The value is the three-element list (+ 1 2), whose first element is the symbol + and whose other two are numbers. quote is a special operator. It returns its argument untouched (like you're quoting cs1 verbatim). Meanwhile (+ 1 2) on its own is 3, an integer, which takes none for length.

So each case asks four independent questions:

FieldQuestion
valueWhat does the form evaluate to, written in the grader's notation?
kindWhich of the course's kinds is the result?
lengthHow many top-level elements does it hold, or none?
operatorFor a compound form, is its head a function, a special operator, or a macro? An atomic form takes none.

nil Is Three Things at Once

The kind field exists because Lisp's most common value refuses to sit in one box. nil is the empty list, a symbol, and false. You need all three.

(symbolp nil)   ; T
(listp nil)     ; T
(null nil)      ; T

No single word describes nil. Any one choice is wrong twice. So the course pins a vocabulary that splits it out:

kindWhat it covers
nullnil, and only nil
consa list with at least one element
symbola symbol that isn't nil, including t
integera whole number
ratioan exact fraction such as 3/4
stringa string
charactera character
functiona function object

nil reads null, never symbol and never cons. t reads symbol. Watch what that does to length. A sequence has a length and everything else answers none, and nil is a sequence, the empty one, so its length is 0 rather than none. That combination, null with length 0, turns up in three of the 16 cases.

The vocabulary above differs from what type-of returns. The Lisp standard lets each implementation answer type-of however it likes, so (type-of 3) can read FIXNUM on one build and INTEGER on another. A published answer table built on it would be wrong somewhere. Hence, the kinds above are defined in scripts/support.lisp and mean the same thing everywhere.

The operator Field Is Where Prefix Evaluation Gets Graded

A compound form puts its head first and its remaining subforms after it. That uniformity hides a distinction. Three different things sit in the head position across these cases. Each one follows a different rule.

A function evaluates every argument, in order, before it runs. +, car, cons, mapcar, and funcall are functions. When you write (+ 1 (* 2 3)), the inner multiplication finishes first and + receives only its value.

A special operator decides for itself which of its subforms to evaluate and when. if evaluates the condition and then one branch. let runs the initializers first, binds the variables, and only then evaluates the body. You can't write any of these as functions because a function's arguments are already evaluated by the time it gets them.

A macro rewrites the form into a different one. The new form gets evaluated instead. defun is a macro. So is lambda.

For the course's operator field, ask in this order. Is the head a special operator? If not, is it a macro? If not, is it a function? First yes wins.

That order settles the overlap. The standard permits an implementation to supply both a special operator and a macro for one symbol, in section 3.1.2.1.2.2, which says an implementation "is free to implement any macro operator as a special operator, but only if an equivalent definition of the macro is also provided." CLISP takes that permission for and, or, when, unless, cond, and case. All six answer yes to both tests. Asking about special operators first is what settles them, so all six read special-operator in this problem set. This course picked that rule. One of the 16 cases lands on it.

Learning Objectives

By the end of this problem set, you should be able to:

  • Predict the value of a prefix form, including which subforms get evaluated and in what order
  • Tell an atom from a list, and explain why nil is both a symbol and the empty list without contradicting yourself
  • Classify a form's head as a function, a special operator, or a macro, and say what changes about evaluation in each case
  • Write a recursive function over a list and identify its base case
  • Pass a function as a value using lambda, #', and funcall, and explain why Common Lisp needs the last two
  • Trace a variable to its binding through a chain of environments
  • Explain the difference between a special variable rebound by let and a lexical variable captured by a closure, using a form where the two disagree
  • Implement an evaluator whose closures capture the environment they were defined in, and say which line makes them lexical

The Rules You Need

An atom is any value that isn't a cons cell. Numbers, symbols, strings, and nil are the atoms in these cases. A cons cell holds two references. A list is a chain of cons cells. (cons 1 '(2 3)) makes a three-element list by putting 1 in front of a two-element one.

Evaluation here has three cases. A number evaluates to itself, while a symbol evaluates to its binding. A compound form follows the rule selected by its head. That's what the operator field asks about.

quote returns its argument untouched. The reader turns a leading ' into a quote form before evaluation ever starts, so '(a b c) and (quote (a b c)) are the same form and both have quote as their head. That matters for the operator field on one case.

car returns the first element of a list and cdr returns the rest. Both answer nil when handed the empty list. That's what lets the usual recursion stop cleanly.

A recursive function over a list tests for the empty list first, then does something with car and recurses on cdr. The base case is (null xs). Use the identity there for whatever you're accumulating. That's 0 for a sum and nil for a list you're building.

mapcar applies a function to every element of a list and collects the results. Because Common Lisp keeps functions and variables in separate namespaces, you hand it a function with #'name for one defined by defun or with a lambda form for an anonymous one. #' is shorthand for function. It asks for the function bound to that symbol. Calling a function you're holding in a variable takes funcall. A language with one namespace needs neither, and Part 2 builds one.

defun defines a function. Its value is the function's symbol. So does defvar, with a variable. Definitions hand back the symbol.

Two kinds of variable live in Common Lisp. They behave differently. That difference is the single most important thing in this problem set. An ordinary let binds a lexical variable, visible only inside the text of the let, and a function written inside that text captures it. The aforementioned defvar declares a special variable, and rebinding one with let changes what every function sees for the duration of that let, however far away those functions were written. Two of the 16 cases are built to disagree with each other on this. If you predict both the same way, one of them is wrong.

Part 2: Build the Evaluator

Now you build the thing that produces the behavior you just predicted.

src/evaluator.lisp implements a small language written in prefix form, the same way Lisp is. It's much smaller than Lisp. Here is the whole grammar:

expr := number
      | symbol
      | (+ expr expr) | (- expr expr) | (* expr expr)
      | (let ((name expr) ...) body)
      | (lambda (name ...) body)
      | (operator-expr argument-expr ...)

An environment is an association list, a list of (name . value) pairs. The empty environment is nil. A lookup walks the list and takes the first pair that matches. An inner binding therefore shadows an outer one for free, with no extra code.

The toy language differs from its host in one way. It has a single namespace, which makes it a Lisp-1. A variable holding a function is callable in operator position, so (f 1) works with no funcall anywhere. Common Lisp has two namespaces and is a Lisp-2. That's why you keep writing funcall and #' in the code that implements it. ANALYSIS.md asks you about that.

The grader scores four groups independently. A pair that reaches E3 and never gets E4 working keeps every mark from E1 through E3. Work in order.

E1: Numbers and Symbols

The two functions below are the smallest evaluator that does anything at all.

lookup takes a symbol and an environment and returns the bound value. The first match wins. An unbound symbol is an error. nil is itself a legitimate value, so a lookup that returns it on failure reads as success. The grader checks both ends of that rule. A binding whose value is nil comes back as nil. An unbound symbol signals an error.

eval-expr takes an expression and an environment. A number evaluates to itself. A symbol goes through lookup.

Order the branches with care. nil is a symbol as well as the empty list, and a number isn't a cons, so test the atoms before you test for a list.

(eval-expr 42 '())              ; 42
(eval-expr 'x '((x . 7)))       ; 7
(lookup 'x '((x . 1) (x . 9)))  ; 1, because the first match wins

E2: Prefix Arithmetic

Two more functions bring the recursion.

eval-operands takes a list of expressions and one environment, and returns the list of their values. This is mapcar over a lambda, in one line. Watch the arity when you write it. eval-expr takes two arguments and mapcar hands its function only one, so the environment comes from the closure.

apply-op takes the operator symbol and the list of already-evaluated operands, and does the arithmetic. Anything that isn't +, -, or * is an error.

Then eval-expr grows a branch. When the head is one of those three symbols, evaluate the operands and apply. Trace the nesting once:

(eval-expr '(* (+ 1 2) (- 10 4)) '())

eval-expr sees *, so it calls eval-operands on ((+ 1 2) (- 10 4)). That maps eval-expr over both, which recurses. The first returns 3, the second 6. eval-operands hands back (3 6) and apply-op multiplies to 18. The recursion is the evaluation. That's why the operands finish before the outer operator runs. That's the function rule from Part 1, now written by you.

E3: let

The two functions below are where the environment starts changing.

extend-env takes a list of symbols, a list of values, and an environment, and returns a new environment with the pairs on the front. mapcar takes two lists and #'cons pairs them up, so this is also one line. Build a new list. Don't modify the one you were handed. The caller keeps using it after your extension goes out of scope. The grader checks that it's untouched.

eval-let handles (let ((name init) ...) body). Evaluate every initializer in the environment you were given, then extend, then evaluate the body in the extended one.

That order is the whole rule. Watch what it buys you:

(eval-expr '(let ((x 1))
              (let ((x 2) (y x))
                (+ x y)))
           '())

The answer is 3. Both initializers of the inner let are evaluated before either symbol is bound, so y gets the outer x and comes out 1. Evaluate them one at a time, binding as you go. Then y would see 2 and you'd get 4. Common Lisp calls the parallel version let and the sequential one let*. You're building let.

The extension also has to end where the body ends:

(eval-expr '(let ((x 1)) (+ (let ((x 2)) x) x)) '())   ; 3

The inner let binds x to 2 for its own body. The trailing x is still 1. If you get 4 here, the inner bindings outlived the body.

E4: lambda and Application

The last two functions carry the idea the whole unit has been building toward.

make-closure takes the parameters, the body, and an environment, and returns the list (:closure params body env). That's all a closure is: the code, plus the defining environment.

The environment you pass is the one eval-expr holds when it meets the lambda. Later call sites are irrelevant. That argument is where lexical scope lives.

apply-closure takes a closure and a list of arguments. It pulls the saved environment out of the closure, extends it with the parameters bound to the arguments, and evaluates the body there. It ignores the caller's environment entirely. Signal an error when the argument count doesn't match, and when what you were handed isn't a closure at all.

Then eval-expr gets its last two branches. A lambda form builds a closure. Anything else with a list head is an application. Evaluate the head to get a closure, evaluate the arguments, and apply. Because the head goes through eval-expr like everything else, a variable holding a closure works in operator position, and so does a lambda form written inline.

(eval-expr '((lambda (n) (* n 2)) 21) '())                    ; 42
(eval-expr '(let ((f (lambda (n) (+ n 1)))) (f 41)) '())      ; 42

Now the case that separates a correct E4 from a plausible one:

(eval-expr '(let ((x 2))
              (let ((f (lambda (y) (+ x y))))
                (let ((x 100))
                  (f 1))))
           '())

Lexical scope gives 3. Dynamic scope gives 101. Every other form this section shows returns the same either way, so this one is the clearest place they part. It carries weight in the rubric to match. If you get 101, apply-closure extends the caller's environment. It must extend the one inside the closure.

The toy language treats functions as ordinary values, so this works too:

(eval-expr '(let ((apply-twice (lambda (g) (g (g 1)))))
              (apply-twice (lambda (n) (+ n 10))))
           '())

The answer is 21. A lambda goes in as an argument, gets bound to g, and is called twice in operator position. Compare what the same idea costs you in the host language, where g would need funcall and the argument would need #'. That comparison is one of the questions in Part 3.

Part 3: Explain the Binding

A complete submission ends with:

91/91 is the complete automated result. The rubric separately assesses your reasoning, your explanation, your commit history, and your workflow runs.

Check the table's form at any time, which reveals no answers:

./lint

./run exits 0 when it prints the case, 64 when it's called with the wrong number of arguments, and 65 when the case id is unknown. ./lint exits 0 when the table is well formed and complete, and 1 otherwise. ./check.sh lists the same form faults before it scores, under a == predictions.tsv form == heading. Read that heading first when it appears. A fault under that heading is a typing mistake.

check.sh exits 0 only when all 91 checks pass. An error inside one of your functions becomes a labeled failed check while the script keeps going. The message prints under the failure. Start at the first one.

The four evaluator groups are isolated from each other on purpose. Delete make-closure. E4's seven checks fail while E1, E2, and E3 stay at full marks. A missing function fails its own checks and leaves the rest green.

One fault in the table's layout stops the grader before it scores anything. The prediction table has to keep its five columns and all 16 ids in order. When it doesn't, the script says so and quits. So a run that ends without a == result == line points at the layout of predictions.tsv. A stray tab, a deleted row, or an editor that turned the tabs into spaces explains it.

Common Pitfalls

  • Predicting symbol for nil. The course vocabulary answers null, and nil is the only value that does.
  • Predicting none for the length of nil. It's the empty list, so it's a sequence, so its length is 0.
  • Predicting macro for and. CLISP answers special-operator for it, and for or, when, unless, cond, and case.
  • Predicting 3 for a quoted arithmetic form. quote doesn't evaluate anything, so the value is the list.
  • Writing a value with spaces in it. The comparison is exact, so (1, 2) is a wrong answer to a case whose result is (1,2). Run ./lint and it prints the line and column of each fault before a check ever scores it.
  • Predicting the same answer for the special-variable case and the closure case. They're built to disagree.
  • Returning nil from lookup when the symbol isn't bound. nil is a value a lookup can legitimately return, so a caller can't tell that apart from success. Signal an error.
  • Evaluating let initializers one at a time, binding as you go. That's let*, and one case is built to catch it.
  • Extending the caller's environment in apply-closure. Every arithmetic case still passes and the scope case returns 101.
  • Modifying the environment in extend-env instead of building a new one. The bindings then outlive the body that introduced them.
  • clisp -q -norc yourfile.lisp prints the Win32 error on Windows. The install is fine. Use ./run and ./check.sh.
  • Running the cases before committing predictions. The Git history would no longer establish which answers were predictions.
  • Editing tests/expected.tsv until the checks pass. The published copy replaces it during grading.
