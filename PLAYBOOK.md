## Native Course Material PDFs

Confirmed 2026-07-14:

- The Markdown material (YAML frontmatter plus body) is the source of PDF content. Every file in `Content/Materials` should attempt to produce a native static PDF, and the Download action should prefer that artifact. **The `downloadLink` half of this entry is superseded by the 2026-09-05 entry below: the key now exempts a material from generation instead of backing it up.** If generation fails, omit only that material's Download action and surface a prominent CI warning/step summary. Bookings, projects, events, and FAQs use separate frontmatter types and must not enter this pipeline.
- PDF generation runs during application startup immediately before BlazorStatic generation. `PdfGeneratorService` discovers non-draft Markdown files recursively from `Content/Materials` itself because BlazorStatic's post collection is not populated at that point. It publishes a per-route `PdfGenerationManifest`. A document-level failure is isolated and never stops the site build. **Resolution order is superseded by the 2026-09-05 entry below: `Blog.razor` reads `downloadLink` first, then the generated PDF, then no Download action.**
- `dotnet run` is the single local and CI entry point. The pinned `Dependencies/RensMarkdownTemplates` project restores its Node dependencies before Tailwind or PDF generation, while application startup bootstraps pinned Pandoc 3.10 and Tectonic 0.16.9 archives for the current Windows/Linux x64 runtime. Downloads use checksums, partial files, retries, extraction staging, and executable validation. Tectonic receives the pinned remote bundle URL and keeps its range cache under `artifacts/tectonic-cache`. It does not download the multi-gigabyte bundle eagerly.
- Frontmatter supports an optional `pdf` map with an allowlisted template name and arbitrary template variables. Templates live under `Dependencies/RensMarkdownTemplates/templates/<name>/`. The selected directory is fingerprinted in full. The default template uses bundle-owned OpenType fonts, native Pandoc highlighting macros, bounded images, and table support, so output does not depend on host fonts or a host TeX installation.
- Each document fingerprint length-frames its logical inputs: generator schema/version, complete raw Markdown, selected template directory, the shared toolchain manifest and `package-lock.json`, Mermaid configuration, referenced local media, and shared PDF assets. Therefore any corresponding frontmatter or body change invalidates that document. Cache state lives in `artifacts/material-pdfs/state`. Content-addressed PDFs live in `wwwroot/pdfs`. Missing, corrupt, mismatched, inactive, or orphaned entries are invalidated/pruned, and both PDF and state publication are atomic.
- Mermaid definitions are rendered as vector PDFs through the shared package's Node CLI entry point and configuration. A Mermaid failure falls back only that document. Process execution uses `ArgumentList`, drains redirected output, distinguishes cancellation from timeout, and kills timed-out process trees.
- Generated PDFs must be excluded from SDK static-web-asset discovery in the early-imported `Directory.Build.props`. BlazorStatic copies the physical directory after startup generation. That same file excludes nested `bin`, `obj`, `tests`, `output`, `artifacts`, and `node_modules`, preventing recursive test/build output from being copied into the main output.
- CI caches toolchain/browser inputs separately from per-document PDF state and generated artifacts. The production run writes a GitHub step summary for generation/fallback outcomes. Local diagnostics and customization are documented in `README.md`.

## Interactive Diagrams

Confirmed 2026-07-15 (marker-based placement update):

- Materials optionally declare `diagrams`, each with `title`, optional `description`, `key` (kebab-case slug), and ordered `steps`. Every step has a `title`, optional `description`, and a complete Mermaid definition in `mermaid`. The contract lives in the shared `MarkdownFrontMatter`, `LearningDiagram`, and `LearningDiagramStep` models.
- Diagrams render ONLY where the body references them with an HTML-comment marker on its own line: `<!-- diagram: key -->`. Unreferenced diagrams never render (strict mode). Same key twice produces two widget instances. Marker determines placement in both web page and generated PDF, achieved by construction: web splits rendered HTML at the verbatim comment, and PDF substitutes the same marker line in body markdown before Pandoc.
- Shared `DiagramMarkers` is the single syntax owner: `MarkerLine` regex for own-line matching, `FindReferencedKeys` for PDF path, `Substitute` for marker replacement, `ResolveSegments` for web path. Key format validated by `KeyFormat` regex (`^[a-z0-9]+(?:-[a-z0-9]+)*$`).
- `Components/InteractiveDiagram.razor` renders diagrams with Previous, Next, and Play controls. `wwwroot/js/interactive-diagrams.js` lazy-loads pinned Mermaid 11.16.0 only on pages with widgets, uses strict security, pre-renders every step before enabling controls, rerenders every step for site theme changes, and preserves authored source when loading or rendering fails.
- Diagram sources must be excluded from `code-features.js` and hidden synchronously before Mermaid loads. Otherwise the raw definition flickers and receives an empty `.code-wrapper`. Do not trust Mermaid's generated viewBox or intrinsic `max-width`: some client renders produced a correctly sized stage with a roughly 40px drawing. Rebuild each SVG viewBox from `.root.getBBox()` plus 8px padding, and enforce fill dimensions inline with `!important`.

Confirmed 2026-09-02 (responsive rendering update, supersedes the fixed-stage guidance above):

- The fixed stage is gone. `.diagram-viewport` fills the article column and scrolls sideways. `.diagram-stage` inside it carries the size the renderer measured. The old `.diagram-canvas` rule (`width: min(100%, 26rem)`, `max-height: 18rem`, `max-width: 26rem !important`) squeezed wide diagrams until labels were unreadable. Measured before the change with the `wideTokenStream` fixture in Chromium: the stage capped at 288px (360px viewport) and 416px (768px and 1280px viewports), and the smallest painted label was **2.07px** and **2.98px**. After the change the same fixture paints **16.58px** and **33.28px** labels with no overflow.
- The renderer picks one of three layouts per widget and writes it to `data-diagram-layout`: `fit` (canonical source scaled to the column), `narrow` (author-approved vertical variant), `pan` (canonical source at a readable width inside a scrolling viewport). The floor is **14 CSS pixels** for a normal label, and **16px** stands in when a drawing carries no measurable label. Painted label size is `computed font-size x (stage width / viewBox width)`, so the whole decision reduces to comparing `available/viewBoxWidth` against `14/labelSize`.
- `narrowDirection` on a diagram is the only reflow opt-in. It accepts `TB` and `BT` only, applies to the first `flowchart`/`graph` declaration line, and preserves every other character of the source. A widget reflows only when **every** step is rewritable, so a walkthrough never mixes layouts. Sequence diagrams and other types therefore always pan. `Models/DiagramNarrowDirection.cs` owns the .NET rules and `rewriteFlowchartDirection` in `interactive-diagrams.js` owns the browser twin. Keep the two regexes in step. Generated PDFs always receive the canonical `step.Mermaid` (`Dependencies/RensMarkdownTemplates/src/RensMarkdownTemplates/Services/PdfGeneratorService.cs:309`); nothing on the .NET side rewrites a definition.
- Every variant renders into an offscreen measurement host attached to `document.body`, never into the visible stage. Detaching the node from the document is not an option: `getBBox` and `getComputedStyle` need layout. The host uses `position:absolute;left:-99999px;visibility:hidden`. A recalculation that fails keeps the previously committed SVG, so a theme change or a resize can never blank a working diagram.
- One `ResizeObserver` per widget, work scheduled with `requestAnimationFrame`, and a width-change guard. The guard is what stops the observer loop: the renderer's own output changes heights, so reacting to anything but a real width change re-enters immediately. A width change inside the same mode resizes with no Mermaid call at all.
- Both the tallest stage height and the tallest complete step height are reserved, so Previous, Next, and Play never move the surrounding page. Horizontal scroll position carries across a step change proportionally. A scroll to a position the renderer did not command stops playback.
- `tests/fixtures/diagram-fixtures.js` hand-mirrors `InteractiveDiagram.razor` so Jest and Playwright share one fixture matrix. That duplication can drift silently, and both suites would keep passing against their own markup while the real article page breaks. `BlogPageTests.DiagramWidgetContract_MatchesTheJavaScriptFixtureBuilder` renders the component and asserts every emitted `data-` attribute appears in the fixture file. Match whole tokens: a substring check accepts a renamed attribute, because `data-diagram-scroll-hint` sits inside `data-diagram-scroll-hintX`. Confirmed red with that exact rename.
- **Superseded 2026-09-02:** the earlier note said no material declared `diagrams`. `Content/Materials/cmsc-124-act3.md` now declares two (`characters-to-token-record` and `scanner-cursor-progress`), neither with a `narrowDirection`, so both pan. Measured in Chromium at a 1280px window: 98px and 301px hidden behind a 541px column.
- **No test may depend on real material existing.** Material gets re-dated, retired, or hidden by the term window and the active-course gate, and a test anchored to a published route then fails for a reason that has nothing to do with the code under test. Use `tests/fixtures/diagram-fixtures.js`, `DiagramFixtures.cs`, or ephemeral frontmatter instead, so tests stay tests. `interactive-diagrams.spec.js` keeps a guard test asserting that the diagram harness requests no `/articles/` route at all. A published article is a place to look with your own eyes, never a fixture.

Confirmed 2026-09-02 (overflow-aware playback, supersedes the fixed two-second interval):

- Play no longer runs on a `setInterval`. One cancellable session per widget drives the walkthrough as a small state machine in `wwwroot/js/interactive-diagrams.js`. Phases are `opening` (10s hold), `pan`, `edge` (5s hold), and `page` (the reduced-motion 10s hold). A step that fits uses the opening hold alone.
- Pan speed is **one viewport width per 8 seconds**, so `readAvailableWidth(state) / 8000` CSS pixels per millisecond. No research names a correct pan speed. This is the agreed comprehension-first default and every value stays a named constant (`PLAY_INITIAL_HOLD_MS`, `PLAY_VIEWPORT_TRAVERSAL_MS`, `PLAY_END_HOLD_MS`, `PLAY_REDUCED_MOTION_HOLD_MS`, `PLAY_REDUCED_MOTION_PAGE_FRACTION`) for later tuning.
- **Holds retuned 2026-09-02 (author call):** every stationary hold is five times the first draft, which had asked a reader to take in a whole diagram in two seconds. Opening 2000 to **10000**, edge 1000 to **5000**, reduced-motion page 2000 to **10000**. `PLAY_VIEWPORT_TRAVERSAL_MS` stays 8000 on purpose: it paces reading while the drawing moves, which is a different problem from how long a still view should last. One step of the pacing fixture now runs about 18 seconds, so every browser test that watches a whole step carries an explicit `test.setTimeout`.
- `state.playback` is both the live session and the generation token. Every timeout and animation frame checks `state.playback === session` before acting, which is what stops a cancelled phase from changing the step later. `pausePlayback` moves the session to `state.paused` and subtracts the elapsed hold. Manual scrolling, Previous, and Next call `stopPlayback`, which discards it, so the next Play starts a fresh walkthrough from the left edge. Play from the last step restarts at step 1.
- The overflow and viewport width are read again on **every** pan frame, so a resize or a theme rerender during playback changes the speed instead of breaking the pan. The pan position lives in the session rather than being read back from the DOM.
- `setScrollLeft` writes `scrollLeft` and then records what the browser actually stored. The browser's own maximum can sit a fraction below the measured overflow, and without the read-back that clamp looks exactly like the reader grabbing the diagram, which stops playback at the right edge. Keep the read-back.
- The live region is written only when the step text actually changes. A pan writes hundreds of scroll updates per step, and every assignment to `textContent` is another polite announcement.
- Reduced motion (`matchMedia('(prefers-reduced-motion: reduce)')`) replaces the pan with static pages of **90% of the viewport width**, so consecutive views keep a tenth in common and nothing falls between two pages. The rightmost view is held like any other before the step changes. `matchMedia` is absent in jsdom, so `createMotionQuery` returns null and the renderer treats that as full motion. A preference change mid-playback cancels the phase and continues the same step from its current position.
- W3C requires pause and resume for scripted scrolling ([SCR33](https://www.w3.org/WAI/WCAG22/Techniques/client-side-script/SCR33)) and recommends suppressing interaction-triggered animation for reduced-motion readers ([SCR40](https://www.w3.org/WAI/WCAG21/Techniques/client-side-script/SCR40)).
- `modestOverflowWalkthrough` in `tests/fixtures/diagram-fixtures.js` is the pacing fixture: measured at a 1280px window it hides 207px behind a 574px viewport, so one pan takes about 2.9 seconds and a browser test finishes quickly. `wideFlowchartWithoutReflow` hides 1198px, over two viewport widths, which is right for reduced-motion paging and far too slow for a full traversal.

## In-Page Navigation (article TOC, FAQ quick links)

Confirmed 2026-08-21:

- **`<base href="/">` rewrites relative `history.replaceState` URLs, not just anchors.** `Components/App.razor` sets `<base href="/" />`, and `replaceState`/`pushState` resolve a relative URL against `document.baseURI`. `history.replaceState(null, null, '#kotlin')` on `/articles/cmsc-124-lab0` therefore produced `https://host/#kotlin`, dropping the article path (on GitHub Pages the base is `/Ren-s-Courses/`, same failure). Dropping `href` from the TOC anchors (the earlier mitigation, still correct for its own reason) never addressed this, because the base URL applies to the History API too. Always pass a path-absolute URL: `location.pathname + location.search + '#' + id`. Same fix applied in `toc.js` and `faq.js`. Reproduce in a browser console: `document.baseURI` vs `location.href`, then `replaceState(null,'','#x')`.
- **Markdown-authored `[text](#heading)` links have the same defect** and are not covered by the TOC handlers. `toc.js` rewrites `.prose a[href^="#"]` to a path-absolute href at init, which fixes the click AND copy-link / middle-click / open-in-new-tab, and lets native fragment navigation (which matches by literal id) do the scrolling. `materials.spec.js` guards the invariant: no `.prose a` may resolve to pathname `/` with a non-empty hash.
- **IntersectionObserver band scroll spies leave dead zones.** The old spy used `rootMargin: '-100px 0px -66% 0px'` and acted only on `isIntersecting` entries, so headings crossing the ~169px band between samples were never highlighted, nothing was active at page top, and a clicked link landed the heading at y=0, above the band, leaving no highlight at all. Replaced with a position check: the last heading whose `getBoundingClientRect().top - TOC_NAV_OFFSET <= 1`, rAF-throttled on `scroll`, applied to desktop and mobile lists together and called directly on click. Deterministic and unit-testable by stubbing `getBoundingClientRect` (jsdom has no layout, so every rect is zeroed by default).
- **`document.querySelector('#' + id)` is wrong for heading anchors.** Markdig `AutoIdentifiers` emits ids containing dots (`build.sh-run` on `cmsc-124-lab0`), which parse as `#build` + `.sh-run` and silently match nothing. An id starting with a digit throws `SyntaxError` outright, which would abort init before listeners are wired. Use `document.getElementById(decodeURIComponent(hash.slice(1)))`.
- **`TOC_NAV_OFFSET` (80px) in `wwwroot/js/toc.js` and `scroll-margin-top: 5rem` on `.prose h1,h2,h3` in `Styles/app.css` are a pair** (the fixed navbar (`NavMenu.razor`, `h-16` = 64.67px measured) otherwise hides the anchored heading at y=0). Keep them in sync. CSS cannot read the JS constant. Verified: heading top lands at exactly 80px after both a TOC click and a `#hash` page load.
- **Init functions must be idempotent about window-level listeners.** `toc.js` stores its handlers on `window.__tocWindowListeners` and `faq.js` on `window.__faqHashListener`, removing the previous pair before re-registering. `faq.js` also marks bound links with `dataset.faqBound`. This was not theoretical: the jest suite re-executes each script per test against one jsdom window, and a duplicate-listener probe measured 10 `scrollIntoView` calls for one `hashchange`.

Confirmed 2026-08-31:

- A position-based scroll spy cannot reach the last heading when the document ends before that heading reaches the navbar line. The at-bottom short-circuit in `wwwroot/js/toc.js` activates the final entry. The browser test keeps this behavior covered.

## Service Worker

Confirmed 2026-09-01:

- `Services/OfflineBundleGenerator.cs` scans the final `output/` directory after static generation. It writes `output/offline-manifest.json` and replaces `__OFFLINE_BUILD_ID__` in `Offline/service-worker.template.js`. The build ID is a lowercase SHA-256 hash of the schema, clean routes, referenced asset URLs, asset bytes, and worker template bytes.
- The manifest contract is `{ schemaVersion: 1, buildId, routes, assets }`. Routes use clean URLs such as `./`, `articles/cmsc-124-lab0`, and `calendar`. Assets use relative URLs within the service worker scope. Both arrays are sorted and deduplicated.
- Run finalization after every output mutation. The order is static generation, feed injection, HTML minification, deployment metadata stamping, then `dotnet run --no-build --project BlazorStaticMinimalBlog.csproj --configuration Release -- --finalize-offline`. The workflow runs this finalizer for both Netlify and GitHub Pages.
- The generated worker uses immutable `ren-courses-offline-<buildId>` snapshots and `ren-courses-offline-meta` status metadata. It fetches the manifest with `no-store`, verifies the embedded build ID, fetches required resources with four concurrent workers, retries transient failures up to three times, stores clean and trailing-slash route aliases, and calls `skipWaiting` only after validation succeeds.
- A same-build install validates the active snapshot before it writes. A complete snapshot receives no cache writes. An incomplete snapshot fetches missing entries and writes only absent entries. Any failed install preserves the active build ID and records the failed build ID.
- Offline metadata always keeps the five fields `activeBuildId`, `state`, `errorCode`, `detail`, and `failedBuildId`. Client-side registration, update, timeout, and repair failures persist through a private worker message before the badge shows `error`. A repair clears error fields only after full snapshot validation.
- `wwwroot/js/site.js` serializes offline operations and passes an operation token through every asynchronous status update. It queries the installing worker during installation, ignores stale worker messages, and accepts a late activation only for the current operation. Repeated `online` events do not start parallel updates.
- A failed install deletes only a new incomplete snapshot. It keeps the active snapshot when a same-build repair fails. Activation validates the snapshot, writes the ready metadata, claims clients, and removes only known Ren snapshot names and legacy `ren-courses-online-first-v2` through `v5` names. It does not delete unrelated application caches.
- Navigation uses network-first behavior. The worker uses the exact clean route and its trailing-slash alias as a three-second fallback. It cancels the network request after the fallback wins. An unknown offline route returns HTTP 503. The worker does not update a cached route after a successful online navigation.
- Playwright Firefox offline emulation does not block loopback fetches made by the service worker. The unknown-route E2E test simulates a real origin outage by closing the fixture network path before navigation.
- The Chromium and Firefox unknown-route tests must both receive the worker-generated HTTP 503 response.
- Local scripts, styles, fonts, media, generated PDFs, Prism files, the web manifest, and Mermaid are exact cache entries. Linked web manifest icons, screenshots, and shortcut icons join the asset inventory when they use local paths. Local asset requests check the active snapshot before the network. The Android banner remains an optional online request and does not block local snapshot installation.
- `Components/App.razor` self-hosts pinned Prism 1.29.0, Mermaid 11.16.0, Inter, and JetBrains Mono files. `interactive-diagrams.js` loads the local Mermaid file only when a diagram needs it. `wwwroot/vendor/THIRD-PARTY-NOTICES.txt` records the licenses.
- `NavMenu.razor` shows a status icon beside Ren's Courses. `wwwroot/js/site.js` exposes the three states `ready`, `updating`, and `error` through `data-offline-state`, an accessible label, and a separate aria-live region. The ready icon checks for updates. The updating icon ignores clicks. The error icon retries installation or repairs missing entries. An unsupported production browser gets a non-actionable message that recommends a current browser. The control does not show status words, a toast, or a document reload.
- Development pages hide the status control and skip service worker registration. Production generation resets the exact `output/` directory before static generation. The generator finalizer removes copied JavaScript tests and stale compressed offline files. Production output must include `service-worker.js` at the deployed application root. The GitHub Pages base path must remain in `Components/App.razor` while the generator emits scope-relative manifest entries.
- To roll back, deploy a byte-changed worker that clears only known Ren caches, unregisters itself, and claims clients. Keep the registration call active until the kill switch reaches installed clients:

```js
const REN_CACHE_PREFIXES = [
    'ren-courses-offline-',
    'ren-courses-offline-meta',
    'ren-courses-online-first-v2',
    'ren-courses-online-first-v3',
    'ren-courses-online-first-v4',
    'ren-courses-online-first-v5',
];

self.addEventListener('install', event => {
    event.waitUntil(self.skipWaiting());
});

self.addEventListener('activate', event => {
    event.waitUntil((async () => {
        const names = await caches.keys();
        await Promise.all(names
            .filter(name => REN_CACHE_PREFIXES.some(prefix => name.startsWith(prefix)))
            .map(name => caches.delete(name)));
        await self.registration.unregister();
        await self.clients.claim();
    })());
});
```

- Verify the generated contract with `dotnet test tests/Ren.Courses.Tests/Ren.Courses.Tests.csproj --configuration Release`. Set `SHOWCASE_MODE=true` for the full browser fixture. Verify the browser flow with `npm run test:e2e` against a fresh production output. On Windows, run `npx playwright test tests/e2e/edge-cases.spec.js --project=msedge --workers=1`. The installed Edge profile remains the final user check: install the deployed PWA, load every generated route once online, close and reopen it offline, open a generated PDF, and test a failed deployment followed by a repaired deployment. Focused offline tests cover worker cache faults and client lifecycle races.
